Server MCP e skill

Un server MCP, Model Context Protocol, espone strumenti e dati a Codex in modo controllato: file, sistemi di build, strumenti di test, seriali, database o servizi interni.

Una skill è una procedura riutilizzabile: istruzioni, criteri, script e controlli che insegnano a Codex come svolgere un'attività ricorrente.

Costruire il contesto

Obiettivo: verificare la correzione del comando seriale X.
Contesto: firmware, protocollo, log precedenti, scheda usata in laboratorio.
Vincoli: non modificare interfacce pubbliche, non cambiare pinout, non eseguire flash senza conferma.
Verifica: compilazione pulita, flash su scheda di test, comando seriale, lettura risposta, controllo JTAG.

Flusso completo di debug firmware con Codex

  1. Analisi iniziale. Codex legge struttura del progetto, punti di ingresso, toolchain e documentazione disponibile.
  2. Riproduzione del problema. Si definisce un caso di prova: comando, stato iniziale, risposta attesa e risposta osservata.
  3. Modifica circoscritta. Codex propone una correzione piccola, motivata e collegata al difetto.
  4. Compilazione. La skill o il server MCP eseguono il comando di build e raccolgono errori, warning e file generati.
  5. Caricamento flash. Solo su hardware autorizzato, con procedura esplicita, versione tracciata e possibilità di ripristino.
  6. Comandi da seriale locale. Il test invia comandi controllati, registra risposte, timeout e log diagnostici.
  7. Verifica JTAG. Quando serve, si controllano registri, memoria, stato del programma e segnali utili alla diagnosi.
  8. Conclusione. Il risultato non è "funziona": è un rapporto con prove eseguite, limiti, file modificati e verifiche mancanti.

Esempi pratici

Prompt di partenza

Analizza il firmware senza modificare i file.
Ricostruisci il flusso del comando seriale SET_TEMP.
Indica dove viene validato il parametro, dove viene salvato e quali test servono.

Compilazione

Compila il progetto con la toolchain configurata.
Se fallisce, separa errori bloccanti, warning e possibili cause.
Non modificare file generati.

Flash su scheda di test

Carica il firmware sulla scheda di laboratorio.
Registra versione, file hex/bin usato, programmatore e risultato del verify.
Non procedere se la scheda non corrisponde al target dichiarato.

Test seriale locale

Apri la porta COM autorizzata.
Invia: SET_TEMP 230
Leggi risposta, timeout e log diagnostico.
Confronta con il comportamento atteso.

Verifica JTAG

Metti un breakpoint dopo il parsing del comando.
Controlla registro stato, valore parametro e ramo eseguito.
Riporta solo evidenze osservate, non deduzioni non verificate.
